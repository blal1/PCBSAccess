# Chapter 6: Reading the Matrix

## Introduction: The Blind Modder's Paradox

Reverse engineering—the process of understanding software you did not write and for which you have no original source code—is the most challenging and rewarding aspect of game modding. It requires intuition, patience, and a deep understanding of software architecture. 

For a blind modder, this process presents a unique paradox. Games are inherently visual. The developers who built the game organized their code, named their variables, and structured their user interfaces based on what appears on a two-dimensional screen. As a blind modder, you cannot look at the screen to see that the "Inventory" button is next to the "Map" button. You cannot see that the "Health Bar" turns red when health is low. 

You must learn to "read the Matrix." You must learn to look at the raw, decompiled C# code and build a mental map of the game's visual and logical structure entirely through text-based search and architectural deduction. This chapter will teach you the methodologies required to navigate millions of lines of unfamiliar code using nothing but your screen reader and your IDE's search function.

---

## 1. The Decompiled Environment

Before you can search, you must understand what you are searching. When you run `ilspycmd` or open a DLL in `dnSpy`, you are not looking at the original code written by the developers. You are looking at a reconstruction.

### The Illusion of Source Code
When C# is compiled into Intermediate Language (IL), certain elements of the original code are lost permanently. The decompiler does its best to guess what the original code looked like, but the result is often messy.

*   **Compiler-Generated Artifacts:** You will frequently see variables named `<>k__BackingField` or `<>c__DisplayClass`. These are auto-generated by the compiler to handle features like properties or lambda expressions (anonymous functions). Do not be intimidated by them. You can usually ignore them or treat them as internal plumbing.
*   **Missing Comments:** All original developer comments (`// TODO: Fix this bug`) are stripped during compilation. You have only the code itself to guide you.
*   **Obfuscation:** Some games use tools to deliberately scramble their code to prevent modding or cheating. If you open a DLL and see thousands of classes named `A`, `B`, `C`, and methods named `a()`, `b()`, the game is obfuscated. Modding an obfuscated game is a nightmare and often not worth the effort unless you are a highly advanced reverse engineer.

### The Power of the IDE
You cannot read decompiled code like a novel. A single game might have 5,000 classes. If you try to read them top-to-bottom, you will fail. 

You must use an Integrated Development Environment (IDE) like Visual Studio or VS Code. These tools index the code, allowing you to jump instantly between references. If you see a method call like `PlayerManager.Instance.GiveGold(50)`, you must be able to press `F12` (Go To Definition) to instantly jump to the `PlayerManager` class and see how `GiveGold` works. Your IDE's search functionality is your primary sense of sight.

## 2. The Search Strategy: Finding the Threads

When you start modding a new game, you are standing in a dark room. Your goal is to find a single thread. Once you find one thread, you can pull it to unravel the entire system.

### Thread 1: String Searching (The Easiest Path)
Games contain text. If you are playing the game and your OCR (Optical Character Recognition) tool or a sighted helper tells you that the screen says "Inventory", or "Not enough mana!", you have your first thread.

1.  Open your IDE's "Find in Files" feature (`Ctrl+Shift+F`).
2.  Search for the exact string, in quotes: `"Not enough mana!"`
3.  The search results will point you directly to the code that displays that message.

If you land in a method named `CastSpell()`, you have just found the combat system. From there, you can look at the variables `CastSpell()` uses. Where does it get the mana cost? Ah, it calls `CurrentSpell.ManaCost`. You pull the thread. You press `F12` on `CurrentSpell`. You are now in the spell database.

### Thread 2: The Prefix Search (Architectural Guessing)
If you don't have a specific string to search for, you must guess how the developer named their classes. Unity developers are remarkably consistent in their naming conventions.

Open your search tool and search for class definitions using regular expressions (Regex) or simple wildcards.
*   `class *Manager` -> Yields `GameManager`, `UIManager`, `InventoryManager`.
*   `class *Controller` -> Yields `PlayerController`, `CameraController`.
*   `class *UI` or `class *Screen` -> Yields `MainMenuUI`, `OptionsScreen`.

When you find a `UIManager`, look at its methods. You will likely find a `public void ShowMenu(MenuType type)` method. This is a massive discovery—you have just found the central hub for all UI in the game.

### Thread 3: The Input Search (Finding the Player)
Every game must process player input. If you want to find the code that controls the player character, search for the Unity input methods.

1.  Search for `Input.GetKeyDown`.
2.  Search for `Input.GetButtonDown`.
3.  Search for `KeyCode.Space` or `KeyCode.Escape`.

If you find a class that says `if (Input.GetKeyDown(KeyCode.Space)) { Jump(); }`, you have found the player controller.

## 4. The "Matrix" Technique: Comparing Live vs. Static

Searching static code is powerful, but sometimes it leads to dead ends. You might find a class called `Btn_Accept`, but you have no idea where it is on the screen or when it is active.

To solve this, we use the "Matrix" technique: combining static code analysis with live memory probing.

### The UnityExplorer Tool
UnityExplorer is an incredible modding tool created by the community. It injects a UI into the game that allows you to browse the live hierarchy of `GameObjects` and inspect their components in real-time. 

While the UnityExplorer UI itself is heavily visual and difficult for screen reader users to navigate directly, it has a powerful search function and can log its output. If you can enlist a sighted helper for just 10 minutes, or if you learn the exact hotkeys to dump its data to a text file, it is invaluable.

### The Live Probe
If you cannot use UnityExplorer, you can write your own "Live Probe" directly in your mod.

Imagine you are trying to make the Main Menu accessible, but you don't know the names of the buttons. You can write a temporary Harmony patch that runs every time *any* button is clicked.

```csharp
[HarmonyPatch(typeof(UnityEngine.UI.Button), "OnPointerClick")]
public class ButtonProbePatch {
    static void Postfix(UnityEngine.UI.Button __instance) {
        // When any button is clicked, log its name and its parent's name
        string btnName = __instance.gameObject.name;
        string parentName = __instance.transform.parent?.name ?? "No Parent";
        
        DebugLogger.Log($"[PROBE] Button Clicked: {btnName}. Parent: {parentName}");
        
        // Try to read its text
        string text = UITextExtractor.GetText(__instance.gameObject);
        DebugLogger.Log($"[PROBE] Button Text: {text}");
    }
}
```

Now, you launch the game, blindly click around the screen until you hear a click sound, and then check your `LogOutput.log` file.
You read: `[PROBE] Button Clicked: Btn_StartGame. Parent: MainMenuCanvas. Text: New Game`.

You now have the exact names of the UI elements. You return to your decompiler, search for `Btn_StartGame`, and you instantly find the `MainMenu` class. You have successfully bridged the gap between the live visual game and the static code.

## 5. Identifying the Singletons (The Entry Points)

In Unity development, a "Singleton" is a class that is designed to have only one active instance at a time. Developers use Singletons to provide global access to important systems. 

For a modder, Singletons are the holy grail. They are the doors that allow your mod to access the game's data from anywhere.

### Searching for Singletons
How do you find them? Singletons almost always follow a specific pattern. They have a `public static` field that holds a reference to themselves.

In your IDE, search for:
*   `public static * instance;`
*   `public static * i;`
*   `private static * _instance;`

When you find one, for example:
```csharp
public class AudioManager : MonoBehaviour {
    public static AudioManager Instance { get; private set; }
    
    public void PlaySound(string soundName) { ... }
}
```
You document it immediately. You now know that from anywhere in your mod, you can type `AudioManager.Instance.PlaySound("beep")` and it will work.

## 6. Documenting Your Discoveries (The API Map)

You cannot hold the architecture of an entire game in your working memory. As you pull threads and discover classes, you must document them. This is the purpose of the `game-api.md` file included in our scaffolding template.

Every time you find a Singleton, a UI Manager, or an important variable, you write it down. 

### A Good API Map Example:
```markdown
## Player Systems
*   **Class:** `PlayerCharacter` (Inherits MonoBehaviour)
*   **Singleton:** `PlayerManager.Instance.LocalPlayer`
*   **Health:** `public float currentHP`
*   **Gold:** `private int _goldAmount` (Requires Reflection!)

## UI Systems
*   **Class:** `UIManager`
*   **Singleton:** `UIManager.i`
*   **Method:** `public void OpenPanel(UIPanel panel)` -> Good Harmony Prefix target!

## Known Keys
*   `KeyCode.I` -> Opens Inventory
*   `KeyCode.Escape` -> Pauses Game
```

If you do not maintain this map, you will spend hours re-searching for the same classes you found yesterday. Furthermore, if you ever share your mod's source code with another developer, this API map is the greatest gift you can give them. It represents hours of painstaking reverse engineering translated into simple, readable facts.

## Conclusion: The Architecture of the Unknown

Reading the Matrix is not a science; it is an art. It requires deductive reasoning. When you see a variable named `isInvOpen`, you must deduce that there is probably a method named `OpenInventory()` nearby. When you see an array of `Item` objects, you must deduce that an `Inventory` class manages it.

You are a detective examining a building through its blueprints. In the next chapter, we will take the threads we have found and use them to identify the "Source of Truth"—the exact locations in the code where the game's state is modified. We will learn how to distinguish between visual noise and actual data, and we will choose the perfect targets for our Harmony patches.
